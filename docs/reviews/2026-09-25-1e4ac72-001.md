### SEC-17-001: Body accumulation is quadratic, and a fetch has no overall time limit

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: resource-abuse
- Where: src/collegium/acquisition/fetching.py:69-73; src/collegium/acquisition/feeds.py:30,52
- Status: new

The problem is the `body += chunk` line. `bytes` has no in-place concatenation, so each chunk copies everything read so far. With the new 20 MB `FEED_MAX_BYTES`, a feed delivered in small chunks (TLS records of about 16 KB) means roughly 1,200 copies averaging 10 MB, several GB of memcpy per fetch. At 3 MB this was negligible. Peak memory stays bounded: about twice the cap, plus up to about 1000:1 gzip or deflate expansion of a single network chunk before the check runs. brotli and zstd are not in the lock file, so those decoders are not available.

The httpx `timeout` is also per operation, not per request. A host that sends a byte just often enough can hold a worker job, or a board request during feed approval, open for a long time.

The exposure is limited:
- `FeedReader` URLs are approved by the owner.
- `find_feed` keeps the 3 MB cap.
- Before this commit `FeedReader` had no size cap at all, so this is still a net improvement.

**Fix:** Collect the chunks in a `bytearray` or a list and `b"".join` them. Consider an overall deadline per fetch, for example by checking `time.monotonic()` against a limit inside the chunk loop.

Notes for the record (not findings):
- Accept header: it used to be a client default, so it was also sent on robots.txt requests and on `find_feed`'s feed candidates. Now it is set per call (`fetching.py:56`). Pages still send the TEXT_TYPES Accept header. `find_feed` candidates now send feed and text types. robots.txt and `types=None` send httpx's default `*/*`. No protection depends on this header.
- `types=None` only skips the content-type filter. The scheme, port, address, redirect, robots and size checks all still apply. `parse_feed` still uses defusedxml. This cannot be abused beyond the size point in SEC-17.
- `find_feed` (`web.py:109`) still uses the 3 MB page cap, so feeds larger than that (such as METR's, about 9 MB) cannot be found through source proposals. This is a functional inconsistency, not a security issue.
- The Dockerfile's `useradd` runs after `COPY` and `uv sync`, so `/app` and `.venv` stay owned by root. The `logins` and `backup` one-shots run `psql`/`sh` directly in the postgres image and therefore still run as root inside that container. They do not handle outside content, so this is unchanged and outside SEC-11's scope.
- Images: all five `image:` lines and the Dockerfile `FROM` are `tag@sha256:<64 hex>` (images.txt). With both tag and digest, Docker uses the digest.
- Secrets scan: the only match is the `SEARXNG_SECRET` default in a context line of compose.yaml, which is unchanged and was reviewed before. The author identity is the same gmail address already public. There is no employer address, and no home path in the diff (only `~/.collegium`).
