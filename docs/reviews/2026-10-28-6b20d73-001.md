## Summary

This push makes `scout._search()` also try known company/organization entities (from `memory.top_entities`, already fetched for the brief, max 10 by that function's existing default) directly against whichever configured discovery sources are name-search registries (`brreg.py`, `prh.py`, newly marked with a duck-typed `name_search = True` attribute, read via the new `Acquisition.name_search_sources()`), in addition to the Scout's own topical queries as before. No secrets, sensitive terms, binary files, dependency or container-image changes appear in the range, and the bundle's own scans came back clean.

On the two areas flagged for attention:

**Resource/budget abuse:** the extra round is bounded on every axis. `memory.top_entities(conn, [domain_id])` is called with its default `limit=10` (unchanged by this diff), so at most 10 distinct names are tried, deduplicated via a set comprehension and filtered to `entity_type in ("company", "organization")`. `name_search_sources()` only returns sources the domain already has configured in `discovery_sources` (an owner-controlled list), and only when non-empty. `_run()` issues one `ctx.acquisition.discover()` call per name per matching source, i.e. at most (10 names) x (configured name-search sources, in practice brreg and/or prh, so 1-2) extra HTTP calls per scout run for that domain — a small, fixed multiplier, not unbounded growth. Neither `BrregDiscovery` nor `PRHDiscovery` sets `metered = True`, so this adds no paid-budget consumption; the daily call budget and `MAX_PAID_PER_RUN` are both untouched.

**Injection/SSRF via entity names in the new HTTP request:** the entity name is passed as an `httpx` `params` dict value (`brreg.py`: `"navn": query`; `prh.py`: `"name": query`), which `httpx` URL-encodes correctly — no raw string concatenation into the URL, headers or a shell command. The request host is the fixed constant `API` base URL in each adapter; the entity name only ever becomes a query-string value on an organization-chosen, hardcoded host, so it cannot redirect the request to an attacker-chosen address (no SSRF). This is the identical pattern already used for the Scout's own LLM-generated topical queries against the same two adapters, so no new class of risk is introduced — only the source of the string going into the same, already-reviewed parameter changes. Results coming back from brreg/prh continue to pass through the existing lead-rendering/fencing and `injection_signals` machinery before ever reaching a model prompt, unchanged by this diff.

No other provenance, audit-trail or least-privilege concerns: the change only adds read-only `discover()` calls through the existing `Acquisition` facade, writes nothing new, and both new tests correctly exercise the gated behavior.
