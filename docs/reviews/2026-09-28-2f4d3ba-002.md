### SEC-42-002: A grounded own-thread reply that exceeds the comment length limit still silently drops with no decision

- Severity: INFO
- Disposition: INFORMATIONAL
- Category: resource-abuse
- Where: `src/collegium/roles/replier.py:124-138`
- Status: new

The SEC-40 fix makes the *acknowledgement* path (`elif own: ...`) unconditionally produce a non-empty, length-bounded (`_subject`'s `MAX_SUBJECT_CHARS=150`) piece of content, so `community.reply_problems()` can never reject it — that specific gap is closed. But the sibling *grounded* path for own threads (`if composed.cited and draft.worth_replying: content = _grounded(ctx, composed)`) has no such bound: `ReplyDraft.points` allows up to 4 model-written statements of unconstrained length, and if the composed content exceeds `MAX_COMMENT` (3000 chars), `prepare()` still returns `lambda conn: "draft too long; not proposed"` with no decision recorded (line 138) — the same failure mode SEC-40 addressed (no decision → not "active" → re-offered by `scout.py` on every later run), just reached through content length instead of a missing `look_into`. This is pre-existing behaviour, unchanged by 2f4d3ba (the same `reply_problems` check sat in the same place before this fix), and unlikely in practice given the model's `max_tokens` budget and the prompt's "one or two sentences" guidance, so it is not treated as blocking.

**Fix (non-blocking, for later):** when `community.reply_problems(content)` fires and `own` is true, fall back to the acknowledgement (or otherwise still record a decision) rather than dropping the comment, so the "always ends in a decision" promise holds for this path too.
