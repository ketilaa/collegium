### SEC-54-001: Grafana admin password defaults to the well-known `admin` if unset

- Severity: MEDIUM
- Disposition: ACTION_REQUIRED
- Category: config
- Where: `compose.yaml` — `GF_SECURITY_ADMIN_PASSWORD: ${COLLEGIUM_GRAFANA_ADMIN_PASSWORD:-admin}`
- Status: new

Every other credential this project wires up fails closed if the owner forgets to set it: `POSTGRES_PASSWORD`, `COLLEGIUM_WORKER_PASSWORD`, `COLLEGIUM_BOARD_PASSWORD`, `COLLEGIUM_PUBLISHER_PASSWORD`, and the new `COLLEGIUM_GRAFANA_DB_PASSWORD` itself (all `:?set ... in .env`). `GF_SECURITY_ADMIN_PASSWORD` was the one exception: with `COLLEGIUM_GRAFANA_ADMIN_PASSWORD` unset, Grafana would start with admin/admin — a classic, trivially guessable default. `GF_AUTH_ANONYMOUS_ENABLED: "false"` is set correctly, but that only blocks anonymous access; it does nothing once the known admin credential is used. On the deployment pattern `docs/operations.md`'s new section documents (a dedicated host on the owner's private network, `COLLEGIUM_GRAFANA_BIND_ADDR` set to that network's address), forgetting only the admin password is enough to leave Grafana reachable with an admin/admin login — full admin access to the dashboards and the proxied Postgres read-only datasource (effectively all of organizational memory readable via ad hoc Explore queries), plus the ability to add further datasources or users.

**Fix:** make `GF_SECURITY_ADMIN_PASSWORD` fail closed the same way every other password in this file does, and make the corresponding `.env.example` line required, not optional/commented alongside the DB password.

**Disposition in this push loop:** Fixed in the next commit (`0140b8a`): `GF_SECURITY_ADMIN_PASSWORD` now uses `${COLLEGIUM_GRAFANA_ADMIN_PASSWORD:?set COLLEGIUM_GRAFANA_ADMIN_PASSWORD in .env}`, and `.env.example` documents both Grafana passwords as required once the `grafana` profile is used.

## Verification detail (the three points specifically checked)

1. **No SQL injection via the dashboard.** All eight panels in `infra/grafana/dashboards/collegium-overview.json` were read in full. Five use `rawSql` against the Postgres datasource — every one is a fixed string with no `${...}`, no `$variable`, and no Grafana template-variable syntax anywhere inside the SQL text. The only `${...}`-style token in the whole dashboard file is `$__range` in the Prometheus panel's `expr` — a Grafana built-in time-range macro for PromQL, not a dashboard variable, and not inside a `rawSql` string at all. Confirmed clean.
2. **`collegium_grafana_app` scoping.** `db/grafana-login.sql` creates the role idempotently, sets its password via the safely-quoted `:'grafana_password'` psql variable, and grants only `collegium_reader` — no write or elevated grant. `collegium_reader` itself is a blanket `SELECT ON ALL TABLES`, the same role already granted to `collegium_worker`; no table holds secrets, API keys or passwords. `grafana-login` and `grafana` both carry `profiles: ["grafana"]`, so neither runs under a plain `docker compose up`; `COLLEGIUM_GRAFANA_DB_PASSWORD` is required only inside those two services, never inside the always-run `logins` service. A deployment that has never set it is unaffected. Confirmed correct.
3. **No real host/IP/secret in `datasources.yaml`.** All three non-Postgres datasource URLs are bare env-var references with no fallback in the YAML itself; the actual defaults live in `compose.yaml` and are generic, unreachable-by-design placeholder hostnames, matching the already-reviewed `COLLEGIUM_LLM_BASE_URL`/`OTEL_EXPORTER_OTLP_ENDPOINT` pattern. The Postgres datasource's password is Grafana's standard provisioning-time env-var expansion, resolved from the required, fail-closed env var — no literal secret committed. Confirmed clean.
