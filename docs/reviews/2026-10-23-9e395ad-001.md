### SEC-49-001: Newly disclosed CVEs in the already-locked `pypdf` and `certifi`

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: supply-chain
- Where: `pyproject.toml`/`uv.lock` (unchanged by this push); `src/collegium/acquisition/web.py:153-173` (`_pdf`)
- Status: new

`pip-audit.txt` lists 8 CVEs against the locked `pypdf==6.19.0` (fixed in 6.20.0/6.20.1/6.21.0/6.21.1) and one against `certifi==2026.7.22` (fixed in 2026.10.19). Every prior review back through 2026-10-16 reported `pip-audit` clean against this same, unchanged lockfile, so these are newly published disclosures, not something this diff introduces. `pypdf` parses PDFs fetched from the open web (research papers, reports -- attacker-reachable content by design), so a crafted PDF exploiting one of these is a real path. Impact is bounded today: `WebReader.extract()` wraps `_read()` (and so `_pdf()`) in a broad `try/except Exception`, so a parsing exception is logged and skipped rather than crashing the worker (`web.py:76-80`); a hang/resource-exhaustion style issue would not be caught that way, but that specific risk is the one already tracked as SEC-29 (no time limit on PDF/HTML parsing, LOW, open). No details beyond ID and fix version were available to assess severity more precisely.

**Fix:** `uv lock --upgrade-package pypdf --upgrade-package certifi` (or equivalent), re-run `pip-audit`, and push as its own small commit through the usual review.

### SEC-50-001: New base-URL overrides for Tavily and Moltbook, unset in production

- Severity: INFO
- Disposition: INFORMATIONAL
- Category: ssrf-and-egress
- Where: `src/collegium/config.py:73-79`, `src/collegium/acquisition/__init__.py:707-727`, `src/collegium/acquisition/tavily.py:15-21`, `src/collegium/acquisition/moltbook.py:29-42`
- Status: new

`COLLEGIUM_TAVILY_BASE_URL`/`COLLEGIUM_MOLTBOOK_BASE_URL`, read only by `acquisition_from_settings`, let `TavilyProvider`/`MoltbookDiscovery` point at an arbitrary host instead of the real one -- needed so `scripts/localtest-smoke.sh` can exercise the real adapters against `local_test_stubs.py` without touching the paid/public services. Both are unset by default and compose only forwards them as `${VAR:-}`, so production's `.env` (which never sets them, per `docs/decisions.md`) is unaffected; the Tavily key would only ever go to the overridden host if this var were mistakenly set in the real environment. Moltbook discovery is keyless, so no credential is at risk there regardless. Noted for the record; no action needed given the current design (opt-in, documented, no production default).
