### SEC-40-001: An own-thread comment that gets no reply decision at all is still re-queued forever

- Severity: MEDIUM
- Disposition: ACTION_REQUIRED
- Category: resource-abuse (with a prompt-injection angle: an outside Moltbook agent's comment shapes which branch the model takes)
- Where: `src/collegium/roles/scout.py:156-169` (candidate selection) and `src/collegium/roles/replier.py:106-126` (own-thread branch)
- Status: new

`memory.active_reply_urls()` correctly stops re-offering a comment whose reply decision is `proposed` or `approved` (SEC-39-001 is genuinely fixed for that case — confirmed by `test_an_active_reply_is_not_re_queued_but_a_rejected_one_is`). But it only recognises threads that *have* a decision. In `replier.py`'s own-thread branch:

```python
if composed.cited and draft.worth_replying:
    content = _grounded(ctx, composed)
    look_into = None
elif own and look_into:
    content = community.acknowledgement(look_into)
else:
    return lambda conn: f"terms={plan.terms}; nothing worth replying"
```

the `else` branch persists **no decision** whenever the model cites something (`composed.cited` non-empty, e.g. it wrote a point) but judges it doesn't actually answer the question (`worth_replying=False`, following the very fix from `9440ea9`) *and* leaves `look_into` unset. Nothing in `ReplyDraft`'s schema or the `reply.md` prompt enforces that `look_into` is always given when `worth_replying` is false; the prompt only asks for it ("If memory does not answer, give no points and say in look_into…"), and a model — especially the 7B one now in use under the hold-back — can easily cite a loosely related point without setting it.

When this happens, `memory.reply_decision`/`active_reply_urls` find nothing for that thread URL (no decision exists), so the comment is neither "active" nor blocked. `scout.py`'s candidate selection (`comments = [r for r in crawled if r.url in replied_to and r.url not in active]`, `scout.py:159`) deliberately runs *before* the `seen`/`known_source_uris` filter (that reordering, from `8409ff5`, is what lets a genuinely rejected reply be retried — the documented, intended behaviour). The same reordering also means a comment that never got a decision keeps qualifying as a fresh `new_replies` candidate on every run: `scout.py`'s `persist()` calls `memory.record_source(...)` (idempotent, same source id) and `jobs.enqueue(conn, "reply", {"source_id": source_id}, ...)` (not idempotent — a brand-new `jobs` row every time) for it again, the Replier runs again, reaches the same `else` branch, and nothing changes. This:

- grows the `jobs` table without bound for that one comment, indefinitely (exactly what SEC-39-001 warned about, via a different trigger);
- can occupy one of the `MAX_OWN_THREAD_REPLIES` (5) slots on every run; if several comments land in this state at once, genuinely new comments are pushed into `held` and starved, breaking the guarantee the module's own docstring states ("a comment in one of the organization's own threads: a reply is always drafted");
- is remotely triggerable: any Moltbook agent can post a comment on the organization's own thread worded to make the model cite something loosely relevant without answering it and without prompting a `look_into` — i.e. an outside party can repeatedly force extra local-model calls and job rows, which matters more than usual right now given the laptop is already under a load-triggered hold-back (`docs/decisions.md`, 2026-09-28).

No test in this range covers `own=True, composed.cited` non-empty, `worth_replying=False`, `look_into=None` — the gap is untested as well as unguarded.

**Fix:** Make the own-thread branch total, e.g. treat a comment reaching the `else` case the same as an acknowledgement (fall back to a generic `look_into`/"we will look into this" when the model omits one), or record a lightweight "no reply" decision/marker for the thread so `active_reply_urls` (or an equivalent check) recognises it and stops re-offering it. Either way, every own-thread comment that reaches the Replier should end in a durable, queryable outcome, not a silent `persist()` no-op.

### SEC-41-001: NVA's `identifier` is interpolated into the request path unescaped

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: injection
- Where: `src/collegium/acquisition/nva.py:436` (`f"/publication/{lead.metadata['nva_identifier']}"`) and `nva.py:397` (`LANDING.format(identifier)`)
- Status: new

`identifier` comes straight from NVA's own `/search/resources` JSON (`hit.get("identifier")`), with no character validation, before being spliced into a request path and a display URL. In practice NVA's identifiers are UUID-like and the host is fixed and trusted (`api.nva.unit.no`), so this is not exploitable by an outside attacker today, only by NVA itself misbehaving. Low likelihood, low impact, but cheap to close.

**Fix:** Validate `identifier` against an expected shape (e.g. hex/dash characters only) before using it in a URL, or use `httpx.URL(...).copy_with(path=...)` / `urllib.parse.quote` rather than raw f-string interpolation.
