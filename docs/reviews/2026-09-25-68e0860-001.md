### SEC-1-001: Vim swap file `.CLAUDE.md.swp` in history, contents not checked

- Severity: MEDIUM
- Disposition: BLOCKING
- Category: privacy (possibly secrets)
- Where: `.CLAUDE.md.swp`, tracked in history until commit 0d84cc7 deleted it
- Status: new

The swap file becomes public with the history even though the tree no longer has it. The bundle's secret scan (`git log -p | grep`) prints only "Binary files differ" for binary files, so the file's contents were never scanned. I can only read files, so I could not extract it from the git objects either.

A vim swap file always contains the local user name, the machine's host name (on a work laptop, often an employer asset name) and the absolute path of the file. It also contains the buffer, which may include text that was never saved to `CLAUDE.md`.

The severity reflects what such files usually hold. It is BLOCKING rather than ACTION_REQUIRED because its contents could not be checked, and a review may not pass what it could not check.

**Fix:** Nothing has been published yet, so the simplest fix is to remove the file from the whole history before pushing: `git filter-repo --invert-paths --path .CLAUDE.md.swp`, then redo the merge with 9142bc4 if needed. Also add `*.swp` / `.*.sw?` to `.gitignore`. Alternatively, add `git log --all --format=%h -- .CLAUDE.md.swp` plus `git show <c>:.CLAUDE.md.swp | strings` to the bundle so the next iteration can inspect it. The `.gitignore` entry is needed either way.

### SEC-2-001: Postgres published on all interfaces, with a default superuser password

- Severity: MEDIUM
- Disposition: ACTION_REQUIRED
- Category: config
- Where: `compose.yaml:7-9` (`POSTGRES_PASSWORD:-collegium`, `ports: "5432:5432"`); default login passwords at `compose.yaml:46-50, 81, 115, 131, 152`
- Status: new

The board and SearXNG are bound to `127.0.0.1`, but the database is published on every interface. If `.env` is missing or incomplete, the superuser password falls back to `collegium`.

On Linux Docker, and on any VM (which the README invites), this exposes a superuser to the network, and Docker's port publishing bypasses host firewalls such as ufw. With the superuser an attacker controls everything: they can act as the `owner` actor, approve decisions and insert rows into the Moltbook outbox, which the publisher would then post. On the owner's laptop, whether the port is reachable from the office network depends on Colima's port forwarding; I could not check that.

Now that the code is public, the defaults matter more than the owner's own `.env`.

**Fix:** Change the mapping to `"127.0.0.1:5432:5432"`. Consider using `${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}` and the same for the three login passwords, so Compose refuses to start without them rather than falling back to known values.

### SEC-8-001: The web reader checks DNS, then connects (DNS rebinding)

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: ssrf-and-egress
- Where: `src/collegium/acquisition/web.py:172-181` (`_check` resolves the name), then `:156` (httpx resolves it again when it connects)
- Status: new

The reader refuses non-public addresses at every hop, which is good. However, the address it checks is not the one it connects to. A hostile page with a very short DNS time-to-live can answer the check with a public address and the connection with a private one. The fetch would then reach an internal host on port 80 or 443, such as an intranet on the owner's office network or the Docker host.

The risk is limited: ports are restricted to 80/443, only GET is used, and nothing leaves the organization except through posts the owner approves.

**Fix:** Connect to the address that was checked. For example, use a custom httpx transport that dials the IP from `_check` and sets the TLS SNI and `Host` header to the name, or check the peer address after connecting (`response.extensions["network_stream"].get_extra_info("server_addr")`).

### SEC-9-001: The feed reader follows redirects without address checks and ignores robots.txt

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: ssrf-and-egress
- Where: `src/collegium/acquisition/feeds.py:36-47` (`follow_redirects=True`, no `_check`, no robots.txt)
- Status: new

The owner approves each feed URL, but a compromised or expired feed host can redirect to a private address. The reader would follow the redirect and parse the response. This is the same protection gap that `web.py` closes. Feeds are machine-readable by intent, so skipping robots.txt is defensible, but that should be a deliberate decision.

**Fix:** Fetch feeds through `WebExtractor._fetch(url, FEED_TYPES)`, which checks addresses at every hop and caps the size. Record in `docs/decisions.md` whether robots.txt applies to feeds.

### SEC-10-001: Container images not pinned by digest; `searxng:latest`

- Status: new

All images come from reputable registries (ghcr.io/astral-sh, the Docker official postgres image, ghcr.io/amacneil, docker.io/searxng), but they are referenced by moving tags. `latest` for SearXNG means any rebuild can pick up an unreviewed version. ### SEC-12-001: Gaps in the push guard (Claude settings deny list, hook scope)

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: other
- Where: `.claude/settings.json:4-8`, `.githooks/pre-push:31`
- Status: new

Three gaps:

- **The deny list misses some bypasses.** It does not cover `git config --unset core.hooksPath`, `git config --local core.hooksPath ...`, or git's abbreviated long options (`git push --no-veri`).
- **One entry targets the wrong option.** `git push -n` is `--dry-run`, not `--no-verify`.
- **The hook accepts any change under `docs/reviews/`.** Any file changed there after the review is accepted, not only report files, so `README.md` or other files could change after a PASS.

The hook is a self-discipline control and cannot be enforced on the client in any case.

**Fix:** Deny `Bash(git config*core.hooksPath*)` and `Bash(git push*--no-v*)`. Limit the hook's post-review allowance to new files matching `docs/reviews/[0-9]{4}-..-..-*.md`. Optionally, enforce the rule on the server with a GitHub ruleset or a required status check.
