I reviewed the `8a3f720` code itself: `llm.py`'s new `Tool` dataclass and `_run_tools` loop run the tool round with no `response_format` (confirmed by the new test asserting `"response_format" not in requests[0]`), feed results back as `role: "tool"` messages, and only then make a separate schema-constrained call — matching the documented reason (`docs/decisions.md`, empirically observed llama.cpp behaviour: `tools` + `response_format` together makes the model skip the tool and fabricate sources). `answerer.py`'s `recall()` tool still routes all outside/excerpt text through `brief()`, which still wraps excerpts in `fence()` unchanged (`answerer.py:347`) — the prompt-injection surface is unchanged from before this commit, just reached via a tool-result message instead of a plain user message. Unknown or failing tool calls are caught (`_run_tools`: unknown name → "Unknown tool"; exception → "The tool failed: {e}"), so a misbehaving tool call can't crash the job. `max_tool_calls=3` bounds the number of round-trips. Tests (`test_llm_calls_a_tool_then_asks_for_the_schema_separately`, `test_an_unknown_or_failing_tool_call_does_not_crash_the_loop`, and the updated `test_ask.py` cases including label-numbering continuation across repeated `recall` calls) look correct against the code by hand.

The one gap — no cap on how many tool calls a single model turn's `tool_calls` array may contain inside `_run_tools`'s `for call in calls` loop, and no test exercising the `max_tool_calls`-exhaustion path itself — is real but low severity: it only reaches local, free, already-rate-limited-by-round-count memory search (`memory.recall`, Postgres full-text search), not any paid or external call, and is further bounded by the 3-round cap on round-trips to the model. This was already identified (as SEC-46-001, LOW/RECOMMENDATION) and the `5791fdd` commit defers it into CLAUDE.md's open-threads list rather than fixing it now.
