### SEC-51-001: The deployment host's real name is written into `docs/decisions.md`

- Severity: MEDIUM
- Disposition: ACTION_REQUIRED
- Category: privacy
- Where: `docs/decisions.md`, new entry "## 2026-10-23 · A way back from the publisher's halt" (added by this diff, `diff.patch` lines ~2384): "...so there was no durable trail of what the original three verification failures actually said either. **Fixed by hand on ai-lab** (`chown`), not a code change."
- Status: new

The project's own convention, reinforced throughout `CLAUDE.md` ("a dedicated hosting server", "the new host" — never named) and by an explicit prior instruction from the owner, is to refer to the deployment host generically in anything that goes into the public repo or a commit message, never by its real machine/Tailscale name. This new entry names it directly: "ai-lab". The sensitive-terms scan did not catch this (it reports "no hits" for the 2 terms currently in `~/.collegium/review-terms.txt`, and CLAUDE.md's own open-thread list notes that list still lacks "machine names" — an acknowledged, not-yet-closed gap), so this is squarely something a human/reviewer check has to catch instead of the automated scan.

This is not a new leak in the sense of first exposure: the same name already appears once, pre-existing and out of this diff's range, at `docs/decisions.md:2311` ("the laptop already pulls ai-lab's backups daily"), introduced in the already-pushed, already-reviewed-and-passed commit `cf6988f` — so the name is already public on GitHub, and that earlier instance slipped past that review too. That does not make a second, new instance acceptable to add; it compounds the exposure and the project has already treated a comparable leak (the sensitive term list, SEC-16/SEC-31) seriously enough to ask GitHub Support for a history purge. I am not recommending a purge for a bare host nickname (low standalone exploitability — no IP, no path, no credential), but the new instance added by this commit should not go in as worded.

**Fix:** Reword the new entry to use a generic term ("the host" / "the server"), consistent with the rest of `CLAUDE.md` and `docs/decisions.md`. Separately, the owner may want to decide whether the pre-existing instance at line 2311 needs the same treatment (a follow-up docs edit, or folding it into the existing GitHub purge request for the old leaked-term commits) — that one is outside this diff's range and not itself blocking this push.

**Disposition in this push loop:** Fixed in the next commit (30366a6): the new entry now reads "Fixed by hand on the host (`chown`)". The pre-existing instance at `docs/decisions.md:2311` is unchanged, out of scope for this push, and left for the owner as noted above.

### SEC-52-001: A granted resume can be silently consumed with no publish attempt made

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: other
- Where: `src/collegium/publisher.py:269-298` (`publish_next`)
- Status: new

`publish_next` consumes the owner's one-time resume grant (`_consume_resume`, marking `used_at`) *before* checking whether there is actually a post ready to send. If, at that tick, no `approved` post exists for a `kind` whose `MIN_INTERVAL` pacing is currently satisfied, the function returns `"nothing to publish now"` right after logging `"resuming: ..."` — the grant is gone, but the halt was never actually tested against a real attempt, so it simply reasserts itself on the next tick. The owner, having just granted a resume and seen it logged as consumed, would reasonably expect the halt to stand or fall on an outcome, not silently vanish with nothing to show for it. This doesn't let anything bypass the owner (the owner still has to grant again) and isn't exploitable, so it's not blocking, but it undercuts the reliability of the fix this commit is making.

**Fix:** Only consume the resume once an actual send is attempted (e.g. move `_consume_resume` after the `post is None` check, or re-check `post is not None` before consuming), or document the current behavior explicitly if it's considered acceptable.

**Disposition in this push loop:** Fixed in the next commit (30366a6): `publish_next` now selects the candidate post first and only calls `_consume_resume` when one exists, so a halt with nothing queued still reports as halted and the grant stays unspent; a new test (`test_a_failed_verification_is_recorded_and_repeated_failures_halt`) covers a valid resume granted while nothing is queued, then consumed once something is.
