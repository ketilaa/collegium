### SEC-30-001: The rewritten report still names a sensitive term, as a lowercase example

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: privacy
- Where: `docs/reviews/2026-09-25-aeb2000-003.md:139`, in commit 8e25a1e and every later tree
- Status: new

The paragraph under SEC-16-003 says the old pattern was case-sensitive, "so a lowercase `…` (in a path, say) would slip past it". The quoted word is not generic: lines 152 and 169 of the same report show it is the name of the earlier project, which the first push's filter-repo pass removed from every commit (SEC-6). This report brings it back in the same file the current rewrite edits. The impact is small (the project is retired, and much of the name can be inferred from a public name kept by design), and the bundle's 2-term scan does not cover this term. This rewrite is the cheap moment to fix it; later means another force push. The word is not repeated here, since this report will be committed.

**Fix:** Add a second replacement for that one example word on line 139 to the same `--replace-text` pass, then regenerate the bundle. Consider adding the name to `~/.collegium/review-terms.txt`, with the exclusion the scan needs for the public account name.

### SEC-31-001: The leaked list stays reachable on GitHub after the force push, and the new history points to it

- Severity: MEDIUM
- Disposition: RECOMMENDATION (deviation: this can only be done after the push, and holding the push would keep the leak on main)
- Category: privacy
- Where: GitHub's object store for ketilaa/collegium; the full old hashes in the headers of `docs/reviews/2026-09-28-49dbe25-001.md` and `docs/reviews/2026-09-27-94a1b26-001.md`, and old short hashes in the subjects of the "Security review <hash> ..." commits
- Status: new

A force push moves the branch, but GitHub keeps the old commits: anyone with a hash can still open `github.com/ketilaa/collegium/commit/<hash>` and browse its tree until GitHub garbage-collects them, which it does not guarantee. Old 49dbe25 and old 3eadef4 both contain the unredacted report. The rewritten history cites the old hashes, which makes them easy to find, and GitHub's events API, any clone or fork made since 2026-09-25, and archives such as Software Heritage may still hold the old history.

**Fix:** After the force push, follow GitHub's "Removing sensitive data from a repository" procedure: ask GitHub Support to purge the dangling commits and cached views for the old hashes (at least old 3eadef4, 49dbe25, 1eadb81, c9bd644, 94a1b26 and the old successors of aeb2000). Check for forks. Treat the person's name and the machine name as disclosed, and decide whether anything depends on the machine name staying private. The stale hashes in reports and subjects are harmless once the objects are purged; leave them.
