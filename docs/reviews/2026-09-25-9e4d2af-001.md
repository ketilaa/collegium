## Summary

This range is one commit, 9e4d2af. It rewrites `SafeFetcher` so that `asyncio.run` drives an async httpx fetch under `asyncio.timeout`, streams robots.txt with a 500 KB cap, and limits `find_feed` to 3 announced feeds within one shared 120 s budget. It fixes SEC-18, SEC-19 and SEC-20. Pages keep every protection they had. Cancellation cannot poison the robots cache or a shared connection pool. No caller can reach `asyncio.run` from a running event loop. One waiting point is still outside the deadline: httpx's own name lookup, which `asyncio.run` waits for when it shuts down (SEC-21). Both are LOW recommendations, so nothing blocks the push.

### SEC-21-001: httpx's own name lookup runs in the default executor, which `asyncio.run` waits for after the deadline

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: resource-abuse
- Where: src/collegium/acquisition/fetching.py:72 (`asyncio.run`), :93 and :140 (`client.stream`, which connects); docs/decisions.md:1109
- Status: new

`_check` does its lookup in `_LOOKUPS`, so the deadline does not wait for it. That part is correct. But httpx then connects through httpcore's AnyIO backend, and `anyio.connect_tcp` resolves the host a second time with `loop.getaddrinfo`. That call runs in the loop's **default** executor. `asyncio.timeout` cancels the await, but `asyncio.run` then calls `loop.shutdown_default_executor(THREAD_JOIN_TIMEOUT)` and blocks until that lookup thread finishes, for up to 300 s on Python 3.12+. The blocking `fetch` call returns only then.

- **Exposure:** an attacker who runs the authoritative DNS for a host can answer `_check`'s query quickly and stall the second one. This is the same position the attacker needs for SEC-8. In practice the stall is bounded by the system resolver's timeouts (resolv.conf; typically tens of seconds), so the overshoot is bounded, not indefinite.
- **Test gap:** `test_a_slow_name_lookup_counts_against_the_deadline` injects `resolver`, which covers only `_check`. `MockTransport` never resolves, so this path is untested.
- **Overclaim:** the new decisions.md entry says the thread pool "also closes the gap left for SEC-8". It does not. SEC-8 is DNS rebinding, caused by exactly this second, independent lookup, and it is unchanged (still deferred by the owner).

The other waiting points are bounded:
- **Stuck lookups in `_LOOKUPS`:** each is left behind in its thread. If all 4 threads are stuck, later lookups queue behind them. Queued ones are cancelled with their fetch, which fails as `Refused` at its deadline and does not hang. This degrades fetching for at most the resolver timeout.
- **CPU work after the fetch** (trafilatura, `parse_feed` on up to 20 MB) is outside the deadline by design. It is roughly linear, apart from SEC-22.
- **Parsing robots.txt** runs inside the coroutine, but on at most 500 KB, which is negligible.

**Fix:** Best: connect to the address `_check` validated, for example with a custom httpcore network backend or transport that is given the resolved IP and keeps SNI and the Host header. That removes the second lookup and fixes SEC-8 too. Cheaper: drive the loop with `asyncio.Runner` and give it a default executor that is shut down with `wait=False`. In either case, correct the decisions.md sentence about SEC-8.

### SEC-22-001: `_FEED_LINK` backtracks super-linearly on a hostile homepage, outside any deadline

- Severity: LOW
- Disposition: RECOMMENDATION
- Category: resource-abuse
- Where: src/collegium/acquisition/web.py:38-40, used at :106 on the first 200 KB of the homepage
- Status: new (the code predates this range; raised because you asked about CPU-bound work after the fetch)

The pattern is `<link\b[^>]*\btype=["']application/(?:rss|atom)\+xml["'][^>]*>`. Suppose a homepage repeats `<link type='application/rss+xml' ` thousands of times with no `>` anywhere:
- At each `<link`, the first `[^>]*` runs to the end of the text and backtracks through every position.
- At every `type=...` it passes, the second `[^>]*` scans to the end again, looking for a `>` that never comes.

That is roughly O(k²·n) for k repeats in n = 200 KB. By my estimate that is minutes to hours of CPU; I could not measure it. It runs in the worker's thread, after `fetch` has returned, so neither the fetch deadline nor the `find_feed` budget can interrupt it, and the single worker stalls. Reach is limited as described in SEC-20: only the Strategist calls `find_feed`, for at most 2 candidate sites per job, and a site is a candidate only after it has been used twice in a domain.

**Fix:** Bound the repeats (`[^>]{0,1000}` in both places), or find the `<link>` tags with `html.parser` or lxml (trafilatura already brings lxml). Add a test with a pathological head that must finish quickly.

### SEC-23-001: robots.txt that redirects, fails or times out is cached as "allow everything"

- Severity: INFO
- Disposition: INFORMATIONAL
- Category: other
- Where: src/collegium/acquisition/fetching.py:129-146
- Status: new (the behaviour predates this range)

Some responses leave the site with no rules, and `_allowed` stores that `None` in `self._robots`. `WebExtractor` and `FeedReader` are long-lived (`acquisition_from_settings`, and the board's single `FeedReader` in web/actions.py:53), so the site stays unrestricted until the process restarts. The cases:
- **Redirects:** `follow_redirects=False` applies to robots.txt too, so a 301 from `http://site/robots.txt` to `https://.../robots.txt`, or from the apex to `www.`, gives "no rules". RFC 9309 asks crawlers to follow up to 5 redirects.
- **Errors and timeouts:** any `Exception` gives "no rules", including httpx's per-read timeout and 5xx responses. RFC 9309 treats 5xx as "disallow all".

The rewrite handles cancellation correctly: a `CancelledError` skips the assignment, so a deadline never caches `None`. A robots.txt truncated at 500 KB keeps the rules it contains, which is correct.

**Fix (optional):** Follow a few same-site redirects for robots.txt. Treat 5xx and errors as "disallow" and do not cache them.

## Earlier findings

This is iteration 001 of a new push loop. From the previous loop (2026-09-25-51408ea-001):
- **SEC-18 (robots.txt uncapped and outside the deadline): fixed.** robots.txt is streamed through `_read` with `ROBOTS_MAX_BYTES` and runs under the fetch's `asyncio.timeout`. The note from SEC-17 still applies: a single decompressed chunk can exceed the cap before the check runs.
- **SEC-19 (handshake and headers outside the deadline): fixed.** Connect, TLS, the request write, the headers and every body read are awaited under `asyncio.timeout`. What remains is SEC-21-001.
- **SEC-20 (every announced feed tried): fixed.** Announced feeds are de-duplicated and capped at 3. All candidates, the homepage included, share one 120 s budget (web.py:98, :115-121).
- **SEC-8, SEC-12, SEC-14 and SEC-16 stay deferred by the owner.** SEC-8 is unchanged (see the overclaim in SEC-21-001). The per-hop scheme, port and public-address check still runs before the robots check and the GET.

Checked and found sound:
- **Page protections:** every hop runs `_check` (scheme, port, `is_global`, not multicast), then robots, then the GET. The loop allows at most `MAX_REDIRECTS + 1` hops. The size cap raises `Refused`. The Accept header comes from `types`, and the User-Agent is set on the client. Before its request, robots.txt gets its own `_check(site)`.
- **No running loop at any caller:** the worker and the CLI are synchronous. The board's `approve_feed` is a sync `def` route, so it runs in Starlette's threadpool with no loop in that thread. The only `async def` in src is the security-headers middleware, which does not fetch. If a caller ever became async, `asyncio.run` would raise `RuntimeError`, so it would fail loudly rather than silently.
- **Cancellation:** a fresh `AsyncClient` per fetch means no shared pool can be left half-closed. `async with` closes the stream and the client on cancellation. `except Exception` in `_load_robots` does not catch `CancelledError`, and `TimeoutError` becomes `Refused` only at `_within`. httpx's own timeouts are `httpx.TimeoutException`, not the builtin `TimeoutError`, so they are not misreported. The `_robots` dict is shared between board threads, which is harmless in CPython.
