## Summary

This range is one commit, d87859f. It replaces the `_FEED_LINK` regex (SEC-22) with a hand scan, `_link_tags`, and corrects the claim about SEC-8 in docs/decisions.md. On ASCII input the scan is linear and always makes progress. However, it searches in `page.lower()` and slices `page` with the same indices. `str.lower()` can make a string longer: U+0130 "İ" becomes "i̇", two code points. With enough "İ" before a `<link` near the end of the text, `start` passes `len(page)`, `end` falls back below `start`, and the loop never ends. Each pass also appends an empty string, so memory grows without limit. Any page with this shape triggers it, whether hostile or just a Turkish page. This is a new regression and worse than SEC-22, so it blocks the push. The fix is small.

### SEC-24-001: `_link_tags` loops forever, and grows memory, when `page.lower()` is longer than `page`

- Severity: HIGH
- Disposition: BLOCKING
- Category: resource-abuse
- Where: src/collegium/acquisition/web.py:147-155 (called at :106 on the first 200 KB of a candidate homepage, from roles/strategist.py:272)
- Status: new (introduced by this commit)

`lower = page.lower()` is not always the same length as `page`. `"İ".lower()` is `"i̇"`, which is 2 code points. After k such characters, indices in `lower` sit k places later than the same text in `page`. The code:
- takes `start` from `lower`;
- sets `limit = min(start + MAX_TAG_CHARS, len(page))`, using the length of `page`;
- slices `page[start:end]`.

Example: `page = "İ" * 10 + "<link"`. Here `len(page)` is 15, and `lower.find("<link")` returns 20. Then `limit` is 15, both `find` calls get an empty range and return -1, and `end` is 15. The loop appends `page[20:15]` (an empty string) and sets `start` to 15. The next `lower.find("<link", 15)` returns 20 again. The loop never ends, and `tags` keeps growing until the worker runs out of memory.

The trigger is any `<link` whose position in `lower` is at or past `len(page)`. That happens when the number of "İ" before it is at least its distance from the end of the decoded 200 KB head. Attackers can build this trivially: fill the page with "İ" and end it with `<link`. It can also happen by accident on a Turkish page with `<link>` tags late in the body, or when the page is cut at 200 KB.

It runs in the worker after the fetch, outside every deadline. The single worker hangs for good. If the job is retried after an out-of-memory restart, the organization stalls again. Reach is as in SEC-20/22: the Strategist, for sites used at least twice in a domain.

Even without the hang, the shifted indices are wrong. After an "İ", slices are off, so real feed links on such pages can be cut or missed. That is also a regression against the old regex.

Progress for ASCII (and any text where `lower` is as long as `page`) holds:
- `page[start]` is `<` and `start+1..start+4` is `link`, so neither `find` can return an index below `start + 5`.
- `limit` is at least `start + 5`, so `end` is greater than `start`.
- Each tag costs at most about 2 × 2,000 characters of C-level `find`, and there are at most n/5 tags, so the work is O(n) with a bounded constant.

**Fix:**
- Do not use indices from a string whose length can change. Either find the tags with `re.finditer(r"<link", page, re.IGNORECASE)`, which is a literal with no backtracking and therefore linear, or search in an ASCII-only lowercase copy (for example `page.translate` with a table for A-Z only, which keeps the length).
- Look for `>` and `<` in `page` itself; case does not affect them.
- As a guard, `assert end > start`, or break when it is not.
- Add a test for `"İ" * 1000 + "<link type='application/rss+xml' href='/f'>"` near the end of the head, and one that finds a feed link placed after many "İ".

### SEC-25-001: The scan cuts a tag at a `<` inside a quoted attribute, which the old regex did not

- Severity: INFO
- Disposition: INFORMATIONAL
- Category: other
- Where: src/collegium/acquisition/web.py:151
- Status: new

You asked whether the scan can miss feed links the old regex found. Apart from SEC-24, here is how it compares with `<link\b[^>]*…[^>]*>`:
- **A `>` inside a quoted attribute:** both stop there, so nothing changes.
- **Uppercase tags and attributes:** handled, through `lower` and `re.IGNORECASE`.
- **Whitespace variants** (`<link\n`, tabs): handled. `< link`: neither matches.
- **Tags longer than 2,000 characters:** the old regex matched them; the scan does not. Real `<link>` tags are far shorter.
- **A `<` inside a quoted attribute** (for example `title="a<b"` before `type=`/`href=`): the old `[^>]*` passed over it; the new scan ends the tag there and loses what follows. This is rare on real pages and has no security impact.
- **`<link` as a prefix of a longer tag name:** the scan now also takes tags such as `<linkedin-x …>`, because it has no `\b`. That is harmless, since `type=` must still match.

**Fix (optional):** None needed. If wanted, skip over quoted values when looking for the end of a tag, still within MAX_TAG_CHARS.
